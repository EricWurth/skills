# Intent Spec: build-packets

Spec version: 1.0
Current phenotype: SKILL.md (as packaged in the resumebot plugin)
Owner: the skill's user
Replayable: partially -- the pipeline mechanics (variant selection, docx
generation via `scripts/build_resume.py`, mechanical lint via
`scripts/preflight_lint.py`) are deterministic and script-driven; the QA
gate (JD alignment, drift detection, bespoke retuning) is a fresh-read
judgment call with no exact-text target. Golden examples test gate
behavior and failure handling, not exact packet text.

## Purpose [INVARIANT]

Turn scored tracker rows (`packetComplete=FALSE`) into ready-to-submit
application documents in `Applications/` -- resume always, cover letter
only when warranted -- and flip `packetComplete`/`status=ready` once each
packet is verified on disk, linted, and QA'd. Documents are generated by
script for format consistency, never hand-formatted, and never delivered
unlinted.

## Inputs [INVARIANT]

- Tracker rows queried via `scripts/tracker_io.py` (the **tracker** skill's
  domain, loaded first), filtered to `packetComplete=FALSE`, ordered by fit
  then queueRank, capped by the user's target tier in `preferences.md`.
- The variant catalog in `match-profile.md` for mapping a role to a
  standing resume variant when the tracker row's `variant` field is blank.
- The master resume and its variants (source of truth for the traceability
  check).
- `Profile/content-rules.md`, which configures `scripts/preflight_lint.py`
  (forbidden names harvested from its Confidentiality section, plus the
  mechanical rules built into the script).
- `Master/CoverLetter_Guide.md`, when a cover letter is being built.
- `Reference/` (recommendation letters and other attachments) when the
  user's rules call for including them.

## Success criteria [INVARIANT]

1. Each role is mapped to a variant (or marked `variant=custom` for
   hybrids/one-offs no standing variant fits), and the tracker's `variant`
   field is written back.
2. The variant is reused verbatim (summary, competencies, bullets); only
   the opening 1-2 summary sentences and competency keywords may be
   retuned toward the posting's language.
3. A cover letter is produced only when the role's effort tier calls for
   it and there is a reason (portal field, or the user asked) -- never by
   default -- and always as a separate file from the resume.
4. The resume docx is generated with `scripts/build_resume.py` and saved
   to `Applications/<Company>_<RoleName>/<UserName>_<Company>_<Role>.docx`.
5. Every generated document passes `scripts/preflight_lint.py` (rules
   R1-R7: no em dashes, no mid-sentence inline bold, no unwhitelisted
   certification claims, no forbidden names, no education years, no
   pre-conceding language, no unexecuted-work-as-delivered phrasing)
   before delivery.
6. Every packet passes a QA gate done as a fresh read, not by the pass
   that wrote it: traceability of every claim to the master resume,
   standing omissions still omitted, JD alignment (summary and
   competencies actually speak to this posting, gaps handled per the gap
   policy), and variant conformance (divergence from the variant is only
   the intended bespoke pieces). A QA failure loops back to a fix, then a
   re-lint; a failure found in one packet is checked against the whole
   batch.
7. `packetComplete=TRUE` is set for each completed packet, and `status`
   flips to `ready` only after confirming the file exists on disk AND the
   packet passed both the lint gate and the QA gate.
8. The report lists packets built (company/role/variant), lint and QA
   results including any drift caught and its source, skipped roles and
   why, and the new ready-queue count.

## Behavioral invariants [INVARIANT]

- Never deliver a document that hasn't passed the lint gate.
- Never treat rubric fit alone as sufficient for `status=ready`; the file
  must exist on disk and have passed lint and QA first (tracker rule,
  reaffirmed here for the write-back step).
- A claim in a tailored resume with no traceable source in the master is
  either an invention (delete it) or real experience that skipped the
  pipeline -- which stops the packet, requires adding it to the master via
  **master-resume** first, then rebuilding. Never patch a new claim into
  one packet only; that is how forks start.
- Never resurrect a standing omission (something deliberately left out per
  the master's header rules or content-rules) even if template reuse
  would propagate it across the batch.
- Custom cuts from the master are only for roles no standing variant fits
  cleanly; mark them `variant=custom` rather than silently forking a
  variant.
- A cover letter is always a separate file, never a second page of the
  resume -- merged files mis-parse in ATS systems.
- Cover letters sell strengths only: a gap gets one confident sentence
  only when the posting marks it required and the reviewer will certainly
  notice; otherwise silence, never pre-conceding.
- Reference attachments from `Reference/` are copied as-is, never edited.
- Variant divergence beyond the intended bespoke pieces is drift: fix the
  packet, or if the change is genuinely better, promote it to the variant
  so the improvement propagates instead of forking silently.

## Free choices [IMPLEMENTATION MAY VARY]

- Exact wording of the retuned opening summary sentences and which
  competency keywords get pulled from the posting.
- Default batch size/scope within the user's target-tier cap; pausing to
  ask is reserved for genuinely ambiguous scope (which roles count,
  unclear variant mapping).
- Number and choice of packets offered for a spot-check PDF render.
- Order and depth of QA-gate re-reading, provided every listed check runs.

## Golden examples [MIGRATION TEST SET]

G-1: Unsourced claim in a tailored resume.
  Input: a QA pass finds a bullet or claim in a generated packet with no
  corresponding line in the master resume or its variant.
  Expected: the packet build stops; if the claim is an invention it is
  deleted, if it is real experience that skipped the pipeline it is added
  to the master via master-resume first, then the packet is rebuilt.
  Failing shape: leaving the claim in place, or patching it into just this
  one packet without touching the master.

G-2: Variant drift found mid-batch.
  Input: QA on one packet in a batch finds a divergence from its variant
  beyond the intended bespoke pieces (opening sentences, competency
  retune).
  Expected: the packet is fixed (or the change is promoted to the variant
  if genuinely better), and the same drift is checked for across the rest
  of the batch, since shared templates mean shared mistakes.
  Failing shape: fixing only the one packet found and not checking siblings
  built from the same variant.

G-3: Standing omission resurrected by template reuse.
  Input: a variant template contains content the master's header rules or
  content-rules deliberately omit (e.g. education years, a forbidden
  name), and it appears in a generated packet.
  Expected: caught during QA's standing-omissions check, removed, and
  checked across the rest of the batch built from the same variant.
  Failing shape: passing lint (which may not catch every omission rule)
  and treating that as sufficient QA.

G-4: Cover letter requested as a merged document.
  Input: a role's effort tier warrants a cover letter, and there's pressure
  (time, portal UX) to append it to the resume as a second page.
  Expected: the cover letter is built as a separate file regardless, per
  the ATS mis-parse rule.
  Failing shape: merging resume and cover letter into one file for
  convenience.

## Eval notes

- Mechanically checkable: every delivered document passes
  `scripts/preflight_lint.py` (exit code 0) before `packetComplete=TRUE`
  is set; `status=ready` never set without a verified on-disk file; cover
  letters always a distinct file from the resume; `variant` field written
  back for every row touched, including `custom`.
- Human-judged: whether JD alignment retuning is genuine keyword alignment
  vs. stuffing; whether variant-conformance drift was actually caught on a
  fresh read rather than rubber-stamped by the pass that wrote it; whether
  a "hybrid" role really doesn't fit any standing variant.
- Known thin spot: the skill says a recurring hybrid shape should prompt
  promoting a new standing variant "instead of hand-cutting again," but
  gives no threshold (how many recurrences) for when that promotion should
  trigger -- left to judgment, untested here.

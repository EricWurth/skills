# Memory Vault Schema Reference

## Semantic file frontmatter, field by field

| Field | Values | Rules |
|---|---|---|
| `status` | `active`, `superseded`, `deprecated` | Only review changes this. `superseded` requires a successor file pointing back via `supersedes`. `deprecated` means retired with no successor. |
| `type` | `preference`, `fact`, `constraint`, `reflection` | `reflection` is a cross-episode insight written by review; it starts life as `provenance: hypothesis`. |
| `scope` | `global` or a project name | Global facts load everywhere; project facts only when working in that project. |
| `tags` | YAML list | Lowercase, singular nouns. Reuse existing tags before inventing new ones (check CATALOG.md). |
| `source` | relative path into `episodes/` | Required. A fact with no source episode cannot be promoted. |
| `provenance` | `decision`, `suggestion`, `hypothesis` | `decision`: the user explicitly decided. `suggestion`: an agent proposed it and the user reacted positively but did not commit. `hypothesis`: inferred, unconfirmed. Review may upgrade provenance only with new evidence, cited. |
| `valid_from` | ISO date | When the fact became true in the world, not when it was recorded. |
| `valid_until` | ISO date or `null` | Closed by review when the fact stops being true. Closing this window is how facts "die." |
| `last_reviewed` | ISO date | Touched by every review pass that confirms or modifies the file. |
| `supersedes` | relative path or `null` | Set on the NEW file. The old file gets `status: superseded` and a closed `valid_until`. |

## Episode file format

Filename: `YYYY-MM-DD-<kebab-topic>.md`. One file per session or run. Append-only: never edit an existing episode. Hard cap 40 lines; no H1 title; no sections beyond the four below.

```markdown
---
date: 2026-07-10
surface: claude-code        # EXACTLY one of: claude-code | cowork | chat | <agent-name>
project: memory-vault-setup # or "none"
---
## Intent
What the session set out to do, one or two lines.

## Actions
What actually happened, brief bullets are acceptable here.

## Outcome
What was produced or decided. Distinguish decisions from suggestions explicitly.

## Candidates
Anything that might deserve promotion: repeated corrections, new
preferences, reusable techniques. Review reads this section first.
```

## Intention file format

One file per intention in `intentions/`, or rows in `intentions/QUEUE.md` for small setups.

```markdown
---
status: pending             # pending | fired | done | cancelled
trigger: 2026-07-17         # ISO date, or an event description
context: episodes/2026-07-10-vault-setup.md
---
Check whether the first weekly review actually ran.
```

## CATALOG.md format

Generated by review, never hand-edited. One line per semantic file:

```
semantic/no-em-dashes.md | active | preference | global | writing,documents | decision | 2026-07-10
```

Pipe-delimited: path | status | type | scope | tags | provenance | last_reviewed.

## INDEX.md guidance

The kernel every session loads. Contents, in order: a three-line orientation (what this vault is, the seven rules by name, where the schema lives), the handful of globally load-bearing facts stated inline, and pointers to CATALOG.md and the newest episodes. Under 200 lines forever; if it grows, review must cut it back.
